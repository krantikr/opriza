## 1. The live stack

Everything runs on free tiers.

```
 Vercel (frontend — marketing site + dashboard, static)
        │  /api/* rewrite  (frontend/vercel.json)
        ▼
 Render (FastAPI backend, Docker)
        │  psycopg over TLS
        ▼
 Neon (PostgreSQL)   ← app connects as a NOSUPERUSER NOBYPASSRLS role

 GitHub Actions ──POST /api/v1/pipeline/cron──► Render   (every ~5 min; also
                  guarded by CRON_SECRET                  wakes the sleeping host)
```

| Piece | Provider | What it is | URL / identifier |
|---|---|---|---|
| Frontend | **Vercel** | Vite build, project `opriza`, root dir `frontend` | <https://opriza.vercel.app> |
| Backend | **Render** | Docker web service `quotation-copilot-api`, free plan, Oregon | <https://quotation-copilot-api.onrender.com> · service `srv-db5jm0g473hc73bds070` |
| Database | **Neon** | PostgreSQL project `quotation-copilot`, branch `production`, free plan, AWS US East 2 (Ohio) | project `floral-flower-39525963` · host `ep-silent-king-b5n5iybj-pooler.c-7.us-east-2.aws.neon.tech` · db `neondb` |
| Cron | **GitHub Actions** | `.github/workflows/email-sync-cron.yml`, every ~5 min | repo `krantikr/opriza` |

when idle — the first request after a lull takes ~30–60 s to cold-start.

## 2. Database

- **Role.** The app connects as `steeldesk_app`, which is `NOSUPERUSER
  NOBYPASSRLS` on purpose. The app **refuses to boot** on a privileged role
  (`app/core/tenancy.py::assert_rls_enforced`), because PostgreSQL exempts
  superusers from every policy, which would silently disable tenant isolation.
  `neondb_owner` also exists (the Neon default) and is **not** what the app uses.
- **Isolation.** Every table carrying `organisation_id` gets a row-level-security
  policy generated by [`scripts/rls.py`](../scripts/rls.py). `rls.py check`
  reports "All 30 tenant tables are protected." Platform-level tables
  (`organisations`, `alembic_version`, `leads`) carry no `organisation_id` and so
  take no policy — this is what lets the public lead-capture route insert on an
  unbound session.
- **Migrations.** Alembic, head applied. The schema was bootstrapped by running
  the baseline migration then `alembic stamp head` (see §5), and migrations since
  apply normally on top.
- **Connection string shape** (password lives only in Render / `deploy.env`):
  `postgresql+psycopg://steeldesk_app:<password>@ep-silent-king-b5n5iybj-pooler.c-7.us-east-2.aws.neon.tech/neondb?sslmode=require`
  — the `+psycopg` prefix is required (psycopg 3); plain `postgresql://` can pick
  the wrong driver.

## 3. Backend environment variables (Render)

Set in the Render dashboard, not in git. `render.yaml` marks the secrets
`sync: false` so they are entered by hand.

| Var | Purpose | Notes |
|---|---|---|
| `DATABASE_URL` | Neon connection (app role) | `postgresql+psycopg://…` |
| `OPENROUTER_API_KEY` | LLM access for the AI stages | AI stages degrade cleanly without it |
| `CREDENTIAL_KEY` | Fernet key; encrypts stored mailbox tokens | **Keep a copy** — losing it orphans stored credentials |
| `JWT_SECRET` | Signs sessions | Render auto-generates |
| `CRON_SECRET` | Guards `POST /api/v1/pipeline/cron` | Must match the GitHub secret — see §6 |
| `CORS_ORIGINS` | Allowed frontend origins | the Vercel URL |
| `APP_ENV` | `production` | set in `render.yaml` |
| `POLLING_ENABLED` | `false` in prod | external cron drives sync instead |

Public Firebase `VITE_FIREBASE_*` values (push notifications) are build-time
frontend vars and belong on Vercel, not Render.

## 4. Routing: how one domain serves two apps

The frontend is a single SPA. Logged out, `/` and the marketing routes
(`/product`, `/pricing`, `/about`, `/contact`) render the public site; signed in,
every route renders the trader's dashboard (`App.tsx` decides). `vercel.json`
rewrites `/api/*` to the Render backend and sends everything else to
`index.html`. There is **no hardcoded backend URL** in the frontend — the dev
proxy (`vite.config.ts`) and the prod rewrite (`vercel.json`) are the two places
that point `/api` at the backend, and they must stay in sync.

The public **Request-access** form posts to `POST /api/v1/leads`, an
unauthenticated route that stores design-partner requests in the platform-level
`leads` table (honeypot drops bots). The team reads leads from the admin console,
never from the public surface.

## 5. Deploying

### The normal path

```bash
# Put the Neon URL in a git-ignored file (so it stays out of shell history):
echo "DATABASE_URL='postgresql+psycopg://steeldesk_app:…@ep-silent-king-…neon.tech/neondb?sslmode=require'" > deploy.env

# Then:
scripts/deploy.sh                 # full deploy, prompts before push
scripts/deploy.sh --no-push       # run all checks, stop before pushing (safe)
scripts/deploy.sh --yes           # no confirmation prompt
```

[`scripts/deploy.sh`](../scripts/deploy.sh) runs the test suites, typecheck and
build; migrates the production DB and re-checks RLS; pushes `main` (which triggers
Render and Vercel to redeploy from GitHub); then polls `/health` and the site.
Other flags: `--skip-tests`, `--skip-migrate`.

Auto-deploy is on for both hosts, so a plain `git push origin main` also deploys —
the script just wraps it with the right pre-flight and verification. The Render
container runs `alembic upgrade head` on boot, so migrations apply even if the
script's migrate step is skipped.

### Why the baseline needed a stamp (history)

On a fresh database, running every migration in sequence failed: the baseline
migration builds the full current schema from model metadata
(`Base.metadata.create_all`), and a later migration then tried to `ADD COLUMN`
one the baseline had already created (`column "direction" already exists`). The
production DB was bootstrapped by running the baseline alone and then
`alembic stamp head`. New migrations written after that point apply normally;
this only bites a from-scratch rebuild, which should repeat the stamp.

## 6. Known issues / outstanding

- **Cron secret mismatch (open).** The GitHub Actions `CRON_SECRET` and Render's
  `CRON_SECRET` currently differ, so the scheduled `POST /api/v1/pipeline/cron`
  returns `401` and email sync does not run automatically. Fix: copy Render's
  `CRON_SECRET` value (Environment → show) into the GitHub repo secret
  (`Settings → Secrets and variables → Actions → CRON_SECRET`), then run the
  *Email sync cron* workflow once and confirm a `202`. The request header is
  `X-Cron-Secret`.
- **Undeployed commits.** As of the last update, several commits (the Oprisa
  marketing site, lead capture, favicon rebrand, this doc) are on local `main`
  but not yet pushed, so they are not live. Run the deploy to ship them.
- **Super-admin password.** The seeded operator is `admin@steeldesk.io` with the
  default development password. Change it before relying on the deployment.
- **Free-tier cold start.** First request after idle takes ~30–60 s. The cron
  call absorbs this once it is working; for a live demo, hit the app a minute
  early.

## 7. First-time environment setup

Creating a *new* environment (new Neon project, new Render service, etc.) is the
manual, account-bound part. It is documented step by step in
[`DEPLOYMENT.md`](DEPLOYMENT.md) and summarised in the README's
[Deployment](../README.md#deployment) section. The dependency order is strict:
**Neon → Render (its URL appears) → Vercel rewrite + GitHub secrets**, because
the Render URL does not exist until the service is deployed, and both the Vercel
`/api` rewrite and the GitHub `API_BASE_URL` need it.
